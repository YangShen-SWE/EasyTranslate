## 实际改动与用户影响

- 新DesktopLauncher无参委托原主程序，--diagnose只做离线随包版本、FXML/CSS存在性、依赖类和JNA native加载检查；非法参数不启动UI。诊断输出仅固定阶段/异常类型，不泄露任意外部异常消息/个人路径/配置；不载入控制器/Preferences/HTTP/全局钩子。未改变原主应用、控制器、FXML、CSS或现有Maven运行入口。
- 新AppImageBuilder用当前pom版本和已验证JAR，构造独立UUID输出目录，以完整JDK25.0.4的系统jmods为单一JavaFX来源，运行jlink及jpackage --type app-image。运行依赖只准三份Jackson/两份JNA，排除Maven FX jar与测试依赖，拒绝未知/重复/缺失输入；不升级依赖，不clean/覆盖旧产物。
- 显式随包JNA Windows x64 jnidispatch.dll到app/native，固定jna.boot.library.path=$APPDIR/native、jna.nounpack=true、jna.nosys=true；不依赖默认临时解包/系统库。应用JAR和DLL核对复制前后字节一致。单独固定java.logging（JNA实际依赖）及HTTP/Prefs/XML/FX/加密/本地化等闭包。
- 新AppImageVerifier核对启动入口/app-version、必需文件/模块、当前应用JAR版本、单一FX来源及禁止临时解包选项；实际执行随包EXE --diagnose并检验版本/运行时输出，失败不生成成功证明。
- 新安装首用说明明确历史README2.1.0下载不是本开发版，保存不等于鉴权成功，镜像并非完全便携数据，卸载/删目录默认保留Java Preferences和DPAPI密文。不读取或删除真实数据/凭据；完整干净Windows、安装器/卸载与API验收保留待验。

## 发现并处理的失败

首个镜像静态检查已过，但EXE --diagnose退出1，未声称通过。jdeps查JNA为java.base/java.desktop/java.logging；平台JNA单独jdeps因缺com.sun.jna退出1，补模块路径分析后退出0确认闭包。加入java.logging和相应拒绝测试。

第二镜像诊断明确native阶段UnsatisfiedLinkError；隔离探针只加载JNA不读配置，得到`Failed to create temporary file for /com/sun/jna/win32-x86-64/jnidispatch.dll library: 拒绝访问。`，退出1。没有更改系统权限/ACL/临时目录或全局环境，也未声称根因已修复；将native依赖按标准显式随包，禁止临时解包/系统库搜索，增加DLL缺失和回退选项拒绝断言。最后重新构建和搬迁检查均通过。旧失败目录留本地未删，无跳过/放宽失败断言。
