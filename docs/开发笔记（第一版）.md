# EasyTranslate 开发笔记（第一版）

这个项目起初是想做一个阅读英文时随手可用的小工具：在别的软件里选中词或词组，按 Tab 后让桌面悬浮窗显示原文和译文。后面还想把反复查过的词收进词本，空闲时拿出来复习。
还有个带翻译的英文输入法很感兴趣，但是目前先不碰输入法和 Rime，先把划词翻译做出来当练手了。

## 现在做到哪一步

程序已经能启动一个置顶的 JavaFX 悬浮窗。窗口可以拖动，关闭时会记住位置，下次启动再恢复。在其他程序里按 Tab，程序会尝试读取当前文字选区；如果读到了文本，就更新悬浮窗里的英文和“模拟译文”。Tab 只被观察，不会被程序拦截，原应用仍会收到这个按键。长按 Tab 的重复按下，以及 Alt+Tab，已经在监听层做了区分。

**目前还没有接入真正的翻译服务**
这里的“模拟译文”只是 `模拟译文：` 加上原文，用来验证从选区到界面的完整流程；也没有把词写进数据库，更谈不上复习轮播或词本管理。后续在考虑接入chatgpt/deepseek之类的ai翻译，这样某些专业词汇在不同语境翻译会更准确

手动测试中，Chrome 的选中与取消选中能够区分；部分桌面版软件在鼠标停在选中文字上时可以读到选区；IDE 编辑器目前仍不能可靠取得选区。因此还不能说已经支持所有应用。windows程序的兼容性也需要在后续版本继续验证。

## 我用到的结构和技术

我用 Java、JavaFX 和 FXML 做界面，用 Maven 管理依赖和构建。当前编译目标是 JDK 25，JavaFX 依赖版本是 21.0.6。Windows 全局 Tab 观察用 JNA 调用低级键盘钩子；选区读取用 Windows UI Automation，由 Java 启动一段 PowerShell 脚本完成。窗口坐标保存在 Java 的 `Preferences` 中。

代码按 MVVM 的思路拆开，但没有为了套架构而增加太多类：

- `view`：FXML 和 `FloatingViewController` 管界面事件，包括拖动和关闭窗口。
- `viewmodel`：`FloatingViewModel` 保存界面需要显示的原文和译文，通过 JavaFX Property 让 Label 自动更新。
- `model`：`Translation` 记录一条原文与译文。
- `service`：分别负责观察 Tab、读取选区和提供译文。翻译服务现在是 `MockTranslationService`。
- `usecase`：`TranslateSelectionUseCase` 把“读取选区 → 翻译”串起来；没有取得有效选区时返回空结果。
- `EasyTranslateApplication`：负责创建窗口、组装这些对象，并在 JavaFX 界面线程更新显示。

选区结果分成 `Found`、`None`、`Unknown`：`None` 表示能判断没有选区，`Unknown` 表示当前程序或控件下无法可靠判断。
这样至少不会把“读不到”误认为“没有选中”，也不会直接拿旧剪贴板内容翻译。

做了不少测试但是还拿不准，也许可以下次尝试用复制剪切板作为备选技术，但是那样同样会有不少bug，比如已经复制在剪切板的旧内容怎么办？

## 踩过的坑

Tab 监听经历了取舍。当前实现只观察按键，并把读取选区的工作交给后台线程，不在键盘钩子的回调里执行慢操作；原按键继续传给系统。这样能先验证划词流程，但 Tab 与输入法候选、原应用自己的 Tab 行为之间还有冲突需要处理。暂时不把它描述成一个已经解决的全局快捷键方案。

## 下一步怎么做

1. 选定真正的翻译来源，替换模拟译文，先完成一次“选中文字 → 按 Tab → 显示真实译文”的演示。目前还没想好用什么在线服务
2. 扩大兼容性测试：对不支持 UI Automation 的程序，再评估安全的复制后备方案。
3. 处理异步请求先后顺序。连续按 Tab 时，旧请求可能比新请求晚完成，覆盖新结果；这项已记入[待解决问题清单](待解决问题清单.md)，先不影响当前的单次演示目标。
4. 在显示成功后写入 SQLite 词组日志，再做求助次数、复习权重、高权重词目轮播和词本界面。失败或取消选区不应记账。
5. 最后再研究输入法候选阶段的 Tab / Tab＋空格分流。当前版本不接 Rime，我看了github也有类似的开源项目也许可以去剽窃一下。

项目的完整目标和边界另见[需求文档](requirements.md)。
