# EasyTranslate 开发笔记（第一版）

写于 2026 年 9 月。这个项目起初是想做一个阅读英文时随手可用的小工具：在别的软件里选中词或词组，按 Tab 后让桌面悬浮窗显示原文和译文。后面还想把反复查过的词收进词本，空闲时拿出来复习。目前先不碰输入法和 Rime，专注把划词这条链路做通。

## 现在做到哪一步

程序已经能启动一个置顶的 JavaFX 悬浮窗。窗口可以拖动，关闭时会记住位置，下次启动再恢复。在其他程序里按 Tab，程序会尝试读取当前文字选区；如果读到了文本，就更新悬浮窗里的英文和“模拟译文”。Tab 只被观察，不会被程序拦截，原应用仍会收到这个按键。长按 Tab 的重复按下，以及 Alt+Tab，已经在监听层做了区分。

这里的“模拟译文”只是 `模拟译文：` 加上原文，用来验证从选区到界面的完整流程；**目前还没有接入真正的翻译服务**。也没有把词写进数据库，更谈不上复习轮播或词本管理。这一版更准确地说是划词翻译的技术样机，而不是完成的翻译软件。

手动测试中，Chrome 的选中与取消选中能够区分；ChatGPT 桌面版在鼠标停在选中文字上时可以读到选区；IDE 编辑器目前仍不能可靠取得选区。因此还不能说已经支持所有应用。记事本等程序的兼容性也需要在后续版本继续验证。

## 我用到的结构和技术

我用 Java、JavaFX 和 FXML 做界面，用 Maven 管理依赖和构建。当前编译目标是 JDK 25，JavaFX 依赖版本是 21.0.6。Windows 全局 Tab 观察用 JNA 调用低级键盘钩子；选区读取用 Windows UI Automation，由 Java 启动一段 PowerShell 脚本完成。窗口坐标保存在 Java 的 `Preferences` 中。

代码按 MVVM 的思路拆开，但没有为了套架构而增加太多类：

- `view`：FXML 和 `FloatingViewController` 管界面事件，包括拖动和关闭窗口。
- `viewmodel`：`FloatingViewModel` 保存界面需要显示的原文和译文，通过 JavaFX Property 让 Label 自动更新。
- `model`：`Translation` 记录一条原文与译文。
- `service`：分别负责观察 Tab、读取选区和提供译文。翻译服务现在是 `MockTranslationService`。
- `usecase`：`TranslateSelectionUseCase` 把“读取选区 → 翻译”串起来；没有取得有效选区时返回空结果。
- `EasyTranslateApplication`：负责创建窗口、组装这些对象，并在 JavaFX 界面线程更新显示。

我把选区结果分成 `Found`、`None`、`Unknown`：`None` 表示能判断没有选区，`Unknown` 表示当前程序或控件下无法可靠判断。这样至少不会把“读不到”误认为“没有选中”，也不会直接拿旧剪贴板内容翻译。现在还没有实现复制选区的后备方案，因此不会为了读取文字而改动剪贴板。

## 开发时踩过的坑

最早在 IntelliJ IDEA 创建 JavaFX 项目时，我花了不少时间理清 Maven、`pom.xml`、JDK 和 JavaFX 的关系。Maven 负责依赖和构建，不是程序运行时的“环境配置文件”。后来出现过依赖标红、命令行找不到 `mvnw.cmd`，以及 `JAVA_HOME` 未设置的问题。确认项目目录、让 Maven 下载依赖并把终端的 JDK 路径配置正确后，项目能够编译。JDK 25 运行 JavaFX 21 时还有 native access 警告；它不是当时启动失败的原因，但以后需要单独处理。

界面部分先遇到 FXML 事件处理方法找不到，原因要从 `fx:controller`、`onMouseDragged` 的方法名和签名对应关系查起。之后又有 CSS 资源找不到导致 `getResource(...)` 返回 `null`，以及只能拖动窗口上半部分的问题。我把拖动事件放到整个根容器上，按鼠标按下时的屏幕坐标与窗口坐标计算偏移，再用这个偏移更新窗口位置；样式文件也按资源目录中的实际路径加载。

选区读取比界面更难。先用 PowerShell 单独验证 Windows UI Automation 的 `TextPattern.GetSelection()`：Chrome 可以读，IDE 和 ChatGPT 桌面版表现不一样。后来尝试同时检查有焦点的控件和鼠标悬停处的控件，并向父级查找 `TextPattern`，ChatGPT 桌面版在鼠标悬停时才有可用结果，IDE 仍不稳定。把 PowerShell 脚本从 Java 传给命令行时，嵌套引号还会被破坏，最后改成 UTF-16LE 编码后通过 `-EncodedCommand` 传入。PowerShell 中的多行 `try/catch` 需要作为完整语句执行；在 CMD 里也不能直接运行 `Get-Clipboard` 这样的 PowerShell 命令。这些测试让我意识到，跨应用读取选区并没有一个对所有程序都可靠的单一接口。

Tab 监听也经历了取舍。当前实现只观察按键，并把读取选区的工作交给后台线程，不在键盘钩子的回调里执行慢操作；原按键继续传给系统。这样能先验证划词流程，但 Tab 与输入法候选、原应用自己的 Tab 行为之间还有冲突需要处理。暂时不把它描述成一个已经解决的全局快捷键方案。

## 下一步怎么做

1. 选定真正的翻译来源，替换模拟译文，先完成一次“选中文字 → 按 Tab → 显示真实译文”的演示。若使用在线服务，先明确发送内容和开关，不把密钥提交到仓库。
2. 扩大兼容性测试：继续看 IDE、ChatGPT 桌面版、记事本和文字型 PDF。只有确认当前存在有效选区才翻译；对不支持 UI Automation 的程序，再评估安全的复制后备方案。
3. 处理异步请求先后顺序。连续按 Tab 时，旧请求可能比新请求晚完成，覆盖新结果；这项已记入[待解决问题清单](待解决问题清单.md)，先不影响当前的单次演示目标。
4. 在显示成功后写入 SQLite 词组日志，再做求助次数、复习权重、高权重词目轮播和词本界面。失败或取消选区不应记账。
5. 最后再研究输入法候选阶段的 Tab / Tab＋空格分流。当前版本不接 Rime，也不把输入法部分算作已实现功能。

眼下最重要的不是把所有功能同时堆上去，而是把每一步都做成能复现、能解释的结果。项目的完整目标和边界另见[需求文档](requirements.md)。
